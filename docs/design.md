# 全体設計

ぬい憑きを4人で並行して作るための設計です。AI に実装を頼むときは、この文書と [api.md](api.md)、自分の担当の文書（[tasks/](tasks/)）を渡してください。

## 作るもの

置いたままのぬいぐるみに怨念が宿り、その怨念を鎮めるために、ぬいと一緒に街へ出かけるアプリです。

1. ぬいを登録する。最後に連れ出した日から、怨念の強さが決まる。
2. オープンデータから、出かける先の地点を推薦する。
3. ぬいと出かけ、訪れた地点で写真を撮って記録する。
4. 記録すると怨念が鎮まる。推薦された地点で記録すると、多く鎮まる。

ハッカソンのデモで、この流れが最後まで動くことを目標にします。

## 優先順位

先に must をすべて終わらせ、全員の must がつながって動いてから should に進みます。

| 優先度 | 機能 |
|---|---|
| must | データによる推薦地点の提示、ぬいの登録、訪問と写真の記録、怨念の計算と表示 |
| should | AR による憑依の演出、怨念の強さで変わるセリフ、中間発表で配られるデータの取り込み、鎮まったときの演出 |
| could | 外出の記録から放置日数を自動で数える、SNS への共有 |
| won't | ログイン、複数の利用者、全国のデータ、スマートフォンのアプリ |

## デモのための割り切り

完璧に作らず、デモで確実に動くことを優先します。

- ログインは作らない。利用者は1人とみなす。
- 対象地域は神奈川県川崎市だけにする。使うデータは [data/README.md](../data/README.md) にある。
- 現在地は地図のクリックで自由に変えられる。会場で GPS がずれても、歩いているようにデモできる。録画でデモしてもよい。
- 放置日数は、ぬいを登録するときに手で入れる。「最後に連れ出した日」を入れるだけ。
- 訪問した地点が本当に近いかは確かめない。画面から送られた地点をそのまま信じる。
- データの前処理は本番前に済ませる。結果を `backend/data/spots.json` に置き、本番中に重い処理をしない。
- デモ用のデータを最初から入れておく。ぬい3体と訪問の記録をいくつか登録した状態から始める。

## 構成

| 部分 | 使うもの | 担当 |
|---|---|---|
| データの前処理 | Python、pandas、NumPy | バックエンドA |
| 推薦の処理 | Python | バックエンドA |
| API | Python、FastAPI、SQLite | バックエンドB |
| 画面 | HTML、CSS、JavaScript、Leaflet | フロントA、フロントB |
| AR | MindAR、Three.js | フロントA |

画面はビルドの要らない素の HTML と JavaScript で書きます。React などのフレームワークや npm は使いません。外部のライブラリは CDN から読み込みます。

API のサーバーが画面のファイルも配るので、本番は1つのコマンドで全部が動きます。

## 動かし方

API と画面をまとめて動かすときは、`backend` で次を実行し、`http://localhost:8000/` を開きます。画面は本物の API を呼びます（`js/api.js` の `USE_MOCK` は `false`）。

```bash
pip install -r requirements.txt
python scripts/seed.py
uvicorn app.main:app --reload --port 8000
```

`scripts/seed.py` は、データベースを空にしてから、デモ用のぬい3体と訪問の記録を入れます。デモの前に実行すれば、いつも同じ状態から始められます。

推薦の API は、たとえば `http://localhost:8000/recommend?lat=35.5314&lng=139.6968`（川崎駅）で試せます。テストは `backend` で次を実行します。

```bash
pip install -r requirements-dev.txt
python -m pytest tests
```

推薦地点を作り直すときは、リポジトリの直下で次を実行します。元のデータがなければダウンロードします。作り直したら API を起動し直してください。

```bash
pip install -r data/requirements.txt
python data/prepare.py
```

API がまだないうちは、`frontend` で静的サーバーを動かし、仮の JSON で画面を作ります（`js/api.js` の `USE_MOCK` を `true` にする）。

```bash
python -m http.server 5500
```

## 怨念の計算

怨念は 0〜100 の整数です。計算は `backend/app/grudge.py` にまとめ、画面では計算しません。除霊の量は保存せず、API が返すたびに計算します。

```
放置の点     = min(100, 放置日数 × 2)
基本の除霊   = 推薦地点なら 50、それ以外なら 10
連続減衰後   = max(10, 基本の除霊 − 10 × 同じ場所に続けて記録した回数)
距離係数     = 300m 以内なら 1、3km 以上なら 0、その間は直線で減る
除霊         = 連続減衰後 × 距離係数
怨念         = max(0, 放置の点 − 除霊の合計)
```

- 放置日数は、登録時に入れた「最後に連れ出した日」から今日までの日数です。訪問を記録しても、この日付は変えません。
- 推薦された地点での記録とは、`spot_id` を付けて送った記録です。地図で推薦地点を選ばずに記録したときは `spot_id` を付けず、それ以外の記録になります。
- 「同じ場所」は、推薦地点なら `spot_id`、それ以外なら画面で入れた地点名で判断します。
- 「続けて」は、直前の記録と同じ場所だった場合です。違う場所を挟むと連続回数は 0 に戻ります。同じ場所に続けて記録すると、除霊量は 50 → 40 → 30 → 20 → 10 → 10 のように減ります。この最低値10は、距離係数を掛ける前の値です。距離が遠いと、さらに小さくなります。
- 距離係数は、推薦地点で記録したときだけ使います。記録した位置（`lat`、`lng`）と推薦地点の位置が離れているほど除霊量が減り、3km 以上離れていると除霊できません。推薦地点以外の記録には距離の減衰はありません。
- 推薦地点のカードから記録するときも、画面は現在地を `lat`、`lng` として送ります。地点まで歩いてから記録すると、距離係数が 1 に近くなります。
- 2、50、10、10、10、300、3000 の値は `grudge.py` の先頭に定数として置き、デモを見ながら調整します。
- 除霊量を保存しないので、定数を変えると過去の記録の除霊量も変わり、怨念が再計算されます。

## 除霊量の見せ方

記録する前と記録したあとに、除霊量とその内訳を出します。これで「同じ場所の連続減衰」「距離減衰」「怨念が足りなくて鎮まらなかった」が分かります。

- 記録前は `GET /visits/preview` で除霊量を計算し、ぬいを選ぶ欄の下に `.stats` の3列カードで出します。項目は「除霊量」「基本」「距離」です。補足は `.field-note` で出します。
- 記録後は `POST /visits` の返り値の `calm` を使い、結果画面に「除霊量」の大きな数字（`.result-grudge`、`.result-label`、`.result-to`）と内訳文（`.result-diff`）を出します。
- `calm.amount` は実際に減った怨念、`calm.computed` は距離係数まで反映した除霊量です。怨念が残りより少ないときは `amount < computed` になり、`capped` が true になります。
- 3km 以上離れているときは `computed` が 0 になり、「鎮まらない」ことが分かります。
- 新しい CSS クラスは作らず、既存の `.stats`、`.result-grudge`、`.result-diff`、`.field-note` を使います。`#visit-calm` は `visit.js` が動的に作り、`index.html` は触りません。

## 怨念の段階

画面のゲージの色やセリフは、次の段階で分けます。

| 段階 | 怨念 | 見せ方の例 |
|---|---|---|
| 鎮まった | 0 | 「また連れてってね」 |
| 弱い | 1〜39 | 「…まあ、許してあげてもいい」 |
| 中くらい | 40〜69 | 「最近ずっと置いていくよね」 |
| 強い | 70〜100 | 「ゆるさない…」 |

## Git の使い方

- `main` に直接 push しません。自分のブランチ（`名前/機能`、例: `tkg28/map`）で作り、プルリクエストで `main` に入れます。
- Issue には must、should、could、won't のラベルを付けます。
- API の形を変えたくなったら、コードより先に [api.md](api.md) を直し、全員に伝えます。

## AI に実装を頼むときの決まり

- この文書、[api.md](api.md)、自分の担当の文書を最初に読ませる。
- API の項目名や形を勝手に変えさせない。
- 上の「構成」にないライブラリを足させない。足したいときはチームで相談する。
- 自分の担当でないファイルを書き換えさせない。
- 動作を確かめてからコミットする。
